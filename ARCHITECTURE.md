# Architecture

## Overview

```
vocab-app/
├── server.js            Express server + all API routes
├── setup.js              Creates tables and seeds the default password on first run
├── build-frontend.js     Bundles src/app.jsx -> public/bundle.js, writes public/index.html
├── src/app.jsx            React source (single-file app, no router)
├── public/
│   ├── styles.css         Hand-written CSS (checked in)
│   ├── bundle.js           Generated by build-frontend.js (gitignored)
│   └── index.html          Generated by build-frontend.js (gitignored)
├── vocab.db               SQLite database, created at runtime (gitignored)
└── package.json
```

## Backend

`server.js` is a single Express app. `better-sqlite3` is used instead of the async
`sqlite3` package because the app is small and low-traffic (a household, not a
service) — synchronous calls keep every route handler a few lines with no callback
or promise wrapping needed.

### Schema (created by `setup.js`)

```sql
settings(key TEXT PRIMARY KEY, value TEXT)
lists(id INTEGER PRIMARY KEY, name TEXT UNIQUE, grade_level TEXT,
      practice_mode TEXT DEFAULT 'flip', created_at TEXT)
words(id INTEGER PRIMARY KEY, list_id INTEGER REFERENCES lists(id) ON DELETE CASCADE,
      term TEXT, definition TEXT, created_at TEXT)
```

`settings` holds two rows: `password_hash` (bcrypt) and `session_secret` (random,
generated once so sessions survive server restarts).

`grade_level` and `practice_mode` are set once per list rather than per word.
Both are additive columns — `setup.js` checks `PRAGMA table_info(lists)` and
runs `ALTER TABLE` for any database created before they existed, so existing
installs upgrade in place with no data loss. `practice_mode` is `'flip'`
(the original flip/sort UI) or `'type'` (type-the-answer quiz UI, see
Frontend below); the server validates it against that allowlist on write.

### Built-in Multiplication list

`setup.js` also calls `seedMultiplicationList(db)` on every startup. It's a
no-op if a list named "Multiplication" already exists (a single `SELECT`
guard), so it only ever runs once per database — a teacher who renames or
deletes it won't have it silently reappear. When it does run, it inserts one
list (`grade_level: '3'`, `practice_mode: 'type'`) and all 144 `a × b`
combinations for `a, b` in 1..12 as term/definition pairs, in one
`db.transaction(...)` so it can't leave a partial list behind. Cards are
shuffled client-side per session like any other list (see the practice-mode
state machine below) rather than at seed time, since the seed order doesn't
matter — nothing renders it unshuffled.

### Auth

There's a single shared password gating the **Parent Dashboard** only — not a
per-student account, and not required to practice. `POST /api/login` checks
the password and sets `req.session.authenticated = true`; `requireAuth`
guards every route that creates, deletes, or changes something (lists, words,
the password itself). `GET /api/lists` and `GET /api/lists/:id/words` are
deliberately public — a student opening the page needs to browse lists and
fetch practice content without typing anything first. This means anyone on
the same network/WiFi can *read* list and word content without the password;
only the household's local network sees this server at all (see the
"listens on all interfaces" note above), and only the write routes are
actually sensitive (a stranger could rename your kid's spelling list, not
get at anything private). Sessions are cookie-based (`express-session`,
in-memory store — fine for a household server that isn't horizontally scaled).

### Routes

| Method | Path | Auth | Purpose |
|---|---|---|---|
| GET | /api/session | – | check if logged in |
| POST | /api/login | – | log in with the shared password |
| POST | /api/logout | – | clear session |
| POST | /api/change-password | ✓ | rotate the shared password |
| GET | /api/lists | – | list all vocab lists + word counts (public, for students) |
| POST | /api/lists | ✓ | create a list |
| DELETE | /api/lists/:id | ✓ | delete a list (cascades to its words) |
| GET | /api/lists/:id/words | – | get one list's words (public, for practice) |
| POST | /api/words | ✓ | add a word to a list |
| DELETE | /api/words/:id | ✓ | delete a word |

## Frontend

`src/app.jsx` is one React file with no router — navigation is a simple
`screen` state string in the top-level `App` component: `mode` (the landing
screen, no auth needed) → `student` → `practice` for kids, or `mode` →
`parent-login` (only if not already authenticated this session) → `parent`
for the dashboard. `ModeSelect`'s `onPick` decides whether "Parent Dashboard"
needs the login step by checking `authenticated`, set from `GET /api/session`
on mount. This keeps the whole app easy to trace for a project this size; a
router would be overhead until there are actual deep-linkable pages.

`build-frontend.js` runs esbuild in bundle mode with the automatic JSX runtime
(so there's no need to `import React` in every file... it's still imported in
`app.jsx` here for clarity) and writes a minified `public/bundle.js` plus a
generated `public/index.html` that references it. This runs automatically via
the `postinstall` npm script, so `npm install` alone leaves the app ready to
`npm start`.

### Practice-mode state machine

`StudentPractice` keeps three pieces of state:

- `allWords` — the full shuffled list for this session
- `pile` — the current round's remaining cards (front of array = current card)
- `mastered` — cards marked "Got It!" this session

"Keep Learning" moves the current card to the back of `pile`. "Got It!" moves it
into `mastered`; when `pile` empties, if not everything is mastered yet, a new
round starts with a freshly shuffled set of the still-unmastered words. This is
the "auto-shuffle when pile is empty" behavior from the spec, and it's shared
by both interaction modes below — `advance(gotIt)` doesn't know or care which
UI called it.

Mastery is **not** persisted to the database — every practice session starts
fresh. Persisting a `mastered` flag on `words` (with a reset control) would be
a straightforward extension, but was left out here to avoid ambiguity around
what "already learned" should mean across sessions without a real spec for it.

### Two interaction modes, one state machine

`StudentPractice` renders one of two components for the current card based on
`list.practiceMode`, both driving the same `advance(gotIt)`:

- **`flip` (default)**: `<Flashcard>` + the "Keep Learning" / "Got It!" buttons,
  unchanged from the original design.
- **`type`**: `<TypeAnswerCard>`. Autofocuses a text input on mount (a plain
  `useEffect(() => inputRef.current.focus(), [])`, reliable because the parent
  forces a full remount every card — see below), submits on Enter (native
  `<form onSubmit>` behavior) or a button click, and does a case-insensitive
  trimmed string compare against `word.definition`. Correct answers flash
  green and auto-advance via `advance(true)` after a 450ms `setTimeout`
  (purely so the "✅ Correct!" flash is visible — not a grading delay).
  Incorrect answers flash red, reveal the right answer, and wait for another
  Enter/click before calling `advance(false)`, so the student always sees
  what they got wrong before the card cycles to the back of the pile.

**Forced remount, not a `word.id` effect dependency:** `StudentPractice` keeps
a `round` counter, incremented on every `advance()` call, and renders
`<TypeAnswerCard key={`${current.id}-${round}`} .../>`. A key change forces
React to unmount and remount the component instead of reusing it, which resets
`value`/`status` state and reruns the focus effect unconditionally. This
matters because "Keep Learning" moves the current card to the *back* of `pile`
without changing its length (see `advance` above) — so on the very last
remaining card, `current.id` can repeat between renders, and an effect keyed
on `[word.id]` alone would fail to reset. The `round` counter closes that gap.

### Timer

`elapsed` (seconds) ticks up via a one-second `setInterval` that starts the
moment `StudentPractice` mounts — i.e. "when the list is opened" — and stops
automatically once `done` is true (the effect's own cleanup, gated by `done`
in its dependency array). Shown live in the header (`⏱ m:ss`, via
`formatTime`) and again as the final time on the celebration screen. `restart`
resets it to 0. It runs the same way for both practice modes; nothing about it
is quiz-specific.

## Extending it

Ideas that fit cleanly into the current structure:

- **Per-word mastery persistence**: add a `mastered_at` column to `words`,
  update it from `advance(true)`, add a "reset progress" button in the parent
  dashboard.
- **Multiple students**: add a `students` table and a `student_id` on a new
  `progress` table instead of storing mastery directly on `words`.
- **Hints / difficulty / tags**: additional columns on `words`, surfaced in
  both the parent word editor and the flashcard face.
- **Spaced repetition**: replace the simple shuffle-until-mastered loop with
  a scheduling algorithm (e.g. SM-2) driven by a persisted `progress` table.
